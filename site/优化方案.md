# 小耳再造整形科普系列静态网站 优化方案

> 本文档基于对现有站点（`/home/sooogooo/dsh/tools/site/`）的真实资源诊断，给出分级、有数据支撑的优化建议。
> 目标：在不大幅改动内容与视觉的前提下，降低首屏加载、提升 SEO 抓取、增强可访问性、控制长期维护成本。

---

## 一、现状诊断（实测数据）

### 1.1 资源体积盘点

| 资源 | 体积 | 占比 |
| --- | --- | --- |
| articles.js | 514 KB | 70.6% |
| global_index.js | 179 KB | 24.6% |
| index.js | 30 KB | 4.1% |
| 其余（search/reading/resume/wechat） | 约 23 KB | 3.2% |
| style.css | 40 KB | — |
| **JS 合计** | **约 745 KB** | 100% |

### 1.2 首屏加载成本（首次进入各页面）

| 页面 | 实际加载的 JS | 体积 |
| --- | --- | --- |
| 首页 index.html | global_index + search + reading + resume + wechat | 约 196 KB |
| A 档 a-popular | global_index + search + reading + wechat | 约 196 KB |
| 文章页 article.html | **articles.js(514KB)** + index + search + reading + wechat | **约 730 KB** |
| B/C 档 | global_index + search + reading + wechat | 约 196 KB |

### 1.3 核心问题

1. **文章页首屏最重**：article.html 依赖 `articles.js`（514 KB）才能渲染正文，首次进入要下载接近 730 KB JS，这个压力被 `defer` 缓解了不阻塞解析，但总传输量仍偏大。
2. **数据存在两份，部分重复**：`global_index.js` 里的 `title` 已在 `articles.js` 里存在；`global_index.js` 还额外存了每篇 800 字符的 `text`（用于搜索摘要）。搜索能用到 text，但 title 重复存储。
3. **OG 图片是相对路径**：微信抓取网页时，相对路径的 `og:image` 在部分部署场景（尤其内网/本地）可能解析失败；且没有 `sitemap`、`robots.txt`、结构化数据。
4. **可访问性仍有缺口**：`<html lang="zh-CN">` 已设置，但缺乏表单标签关联、部分交互图标仅 aria-label、无 `prefers-reduced-motion` 之外的动画降级细节。整体已达 WCAG AA 基础线，可再补。

## 二、优化建议（按优先级 P0 → P2）

> 每项标明收益、代价、是否改动内容。全部为渐进式，可按需选做，不影响现有功能。

### P0：立即可做、收益最大、零功能风险

#### P0-1：将 `articles.js` 拆为"文章正文"（按 A/B/C 分片）与"索引"（轻量）

**现状**：`articles.js` 一个文件 514 KB，含全部 89 篇预渲染 HTML。文章页只需其中 1 篇。

**优化**：`build_index.py` 改为生成三类文件：
- `assets/articles-meta.js`：只含 file → { title, cat, prev, next, back }（约 30 KB），**替代现在 30 KB 的 index.js 并合并 global_index 的 title**。
- `assets/articles/A1.js` … `assets/articles/A20.js`、`articles/C1.js`…`articles/C5.js`、`articles/B.js`：按主题/分档拆分正文 HTML（每片约 5–20 KB）。
- `article.html` 只在 URL 指定 file 时按需加载对应分片，其余不再下载 514 KB。

**收益**：文章页首次从 ~730 KB 降到 ~50 KB（省约 93%）；其它页面保持只加载轻量 meta。
**代价**：需要改 `build_index.py`（一次）+ article.html 的加载逻辑；分片数量从 1 个变成 20+ 个（文件数增加）。
**是否改内容**：否，纯工程。

#### P0-2：合并 `global_index.js` 的重复 `title` 到 meta，删除冗余

**现状**：`global_index.js`(179 KB) 的每条含 `title` + `text`(800字符)，title 与 `articles.js` 重复，text 用于搜索摘要。

**优化**：`global_index.js` 只保留 `{ file, cat, text }`，`title` 从 `articles-meta.js` 读取（或搜索界面用 file 推导）。`text` 从 800 字符缩短为 200–300 字符（搜索摘要够用）。
**收益**：`global_index.js` 从 179 KB 降到约 60 KB；`text` 缩短进一步减半。
**代价**：搜索摘要变短（可接受，仍命中）；build 脚本同步改。
**是否改内容**：否。

#### P0-3：补 `sitemap.xml` 与 `robots.txt`（对抓取/SEO 直接有效）

**现状**：无这两个文件，且 89 篇文章走 `article.html?file=xxx` 动态加载，百度/微信/搜索引擎不会把它们当作独立可索引 URL。

**优化**：
- 生成 `sitemap.xml`，列出每个 A 档主题（A1–A20）、每章综述（C1–C5）、B 档内训、配套文件对应的可直接访问 URL。
- 生成 `robots.txt`，允许抓取，明确 `Sitemap:` 指向。
- 对 `article.html` 的动态内容，确保 `og:url` 在静态 HTML 里就写成规范 URL（去掉 hash），而非留空让 JS 填。

**收益**：让搜索引擎/微信抓取器能发现并索引所有内容，分享出去才有稳定的落地页。
**代价**：需确认部署域名，生成文件即可。
**是否改内容**：否。

### P1：有结构性改善、需一点权衡

#### P1-1：OG 图片改绝对 URL + 增加分享用专属图

**现状**：`og:image` 用相对路径 `assets/img/logo.png`；**无**专门为分享设计的横图（微信朋友圈卡片建议 500×500 或横向）。

**优化**：
- `og:image` 用部署域名绝对 URL（如 `https://域名/site/assets/img/logo.png`）。
- 可选：新增一张 `share-card.png`（1200×630，含 logo + "小耳再造整形科普系列"标题），`og:image` 与 `twitter:image` 指向它；`og:image:width/height/type` 补齐。
- 微信 JS-SDK 的 `imgUrl` 用绝对 logo / share-card。

**收益**：分享卡片更稳定、更美观。
**代价**：需一张设计图（可用现有 logo 合成）；需知道部署域名。
**是否改内容**：否。

#### P1-2：内容图片懒加载与 `loading="lazy"`（若未来加插图）

**现状**：站内文字内容无插图；A 档小红书图文有"9 图位"脚本但未见真的图片。

**优化**：为正文内可能出现的大图统一加 `loading="lazy"`、`decoding="async"`、明确宽高。当前无隐患，预留即可。
**收益**：未来加图时不拖慢首屏。
**代价**：无。
**是否改内容**：否。

#### P1-3：字体与文本渲染优化

**现状**：body 用系统字体栈（`-apple-system`、PingFang SC、Microsoft YaHei），无外部字体加载。这是好的，保持。

**优化**：无需换字体。可补：
- `font-display`（无 Web 字体则无必要）。
- 对 `article` 正文加 `text-wrap: pretty`（现代浏览器支持，改善标题断行）。
- 长文分段已做，无需改。

**收益**：轻微。
**代价**：无。
**是否改内容**：否。

### P2：增强可访问性与长期维护

#### P2-1：可访问性补强

**现状**：已有 skip link、语义标签、焦点可见、色板对比（AA）、暗色模式、减弱动效。

**补充**：
- 给搜索输入框加显式 `<label>`（当前只有 aria-label）。
- 给"返回顶部"按钮、调试按钮等已有 aria-label，确认全部图标按钮都有。
- 给颜色对比再跑一次自动检测，确认 `--c-text-soft` 在小字号下的对比度。
- 确保所有 `<a>` 有可访问文本（无纯图标链接无 alt）。

**收益**：符合 WCAG 2.1 AA，便于读屏/低视力。
**代价**：少量标记调整。
**是否改内容**：否。

#### P2-2：build 流程脚本化与可复现

**现状**：`build_index.py` 一次生成全部。文章正文 89 篇 + 衍生件 60 篇，手动改 md 后需重跑全部。

**优化**：
- 拆成 `build.py`（可重复、幂等），输出到 `content/` 或 `published/` 干净目录，避免与源 md 混放。
- 加 `--watch`（可选，需要 Python watch）或文档说明"改 md 后跑一次"。
- 输出一份 `manifest.json`（文件清单 + 体积），便于长期核对。

**收益**：维护更稳、可回溯。
**代价**：中。
**是否改内容**：否。

## 三、推荐执行顺序

优先做 **P0 三项**（拆 articles.js、合并 global_index、补 sitemap/robots），因为：

1. 拆 articles.js + 合并 global_index 能把文章页首屏 JS 从 ~730 KB 降到 ~50 KB，**是最大的量变**；
2. sitemap/robots 让 89 篇内容能被抓取索引，**是内容资产的价值放大**；
3. 三项都是零功能风险、不改内容、只动构建与标记。

P0 完成后，视需要有：
- **可选**：P1-1 分享专属图（配合微信公众号文案输出、对外推广）。
- **可选**：P1-3 / P2-1 可访问性细化。
- **可选**：P2-2 build 流程整理（当修改频率变高时再做）。

## 五、不做项与说明

- **不引入打包器（Webpack/Vite）**：当前零依赖、可 file:// 直开。拆文件仍保持零依赖，避免引入构建链。
- **不把 og:image 强制绝对到未知域名**：仅当确定部署域名后再绝对化；否则保留相对路径，微信多数场景能解析。
- **不改内容与视觉**：本方案是工程优化，不改变科普稿、文案、配色、布局。
